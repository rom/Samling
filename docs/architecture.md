# Architecture

## Overview

Samling is one statically linked Go binary. It contains the HTTP API, the web
client (embedded files), the database migrations and the administration CLI.
The only things outside the binary are the configuration file, the master
key, the database and the stored files.

```
   Browser / installed web app (PWA)            Native app (future)
   Preact + htm client, served by the server    same REST API, bearer token
              │ HTTPS (TLS 1.3), JSON, SSE              │
              ▼                                         ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ samling serve                                                        │
 │                                                                      │
 │  net/http server ── security headers, panic recovery                 │
 │        │                                                             │
 │  router (http.ServeMux, method + path patterns)                      │
 │        │   per route: rate limit → session/CSRF → pending-step gate  │
 │        │              → permission → handler                         │
 │        ▼                                                             │
 │  internal/app   handlers per feature, access checks (ACL), audit log │
 │        │                │                    │                       │
 │  internal/db       internal/blob        internal/crypto              │
 │  SQL + dialect     encrypting store     keys, AEAD, argon2id, TOTP   │
 │        │                │                                            │
 └────────┼────────────────┼────────────────────────────────────────────┘
          ▼                ▼
   SQLite file        local directory            master key
   or PostgreSQL      or S3 compatible store     (file / systemd credential)

 Around the process: systemd sandbox + seccomp filter, Landlock (applied by
 the server to itself), optional SELinux domain.
```

## Source layout

| Path | Role |
|------|------|
| `cmd/samling/main.go` | CLI: `serve`, `admin create`, `admin passwd`, `backup`, `restore`, `decrypt`, `genkey`, `check-config`, `version`; TLS setup and certificate hot reload; graceful shutdown |
| `internal/config` | YAML + environment + defaults, validation, master key loading, blob back-end selection |
| `internal/db` | `database/sql` wrapper (placeholder rebinding, transactions), schema migrations, table list for backups |
| `internal/crypto` | Key derivation, field encryption, blind index, password hashing, TOTP, streaming AEAD, passphrase container |
| `internal/blob` | `Backend` interface with file system and S3 implementations; `Store` encrypts/decrypts around it |
| `internal/sandbox` | Landlock rules |
| `internal/app` | The application: `app.go` (routing, middleware, errors, rate limiter, activity log), `auth.go`, `acl.go`, `people.go`, `chat.go`, `files.go`, `lists.go`, `polls.go`, `calendar.go`, `meetings.go`, `search.go`, `backup.go`, `routes.go` |
| `web/` | `embed.go` embeds `web/static/` (the client) into the binary |
| `scripts/`, `deploy/` | Installation, certificates, backups; systemd, SELinux, seccomp |

## Request flow

1. `App.ServeHTTP` recovers panics and sets the security headers
   (CSP, `nosniff`, frame denial, referrer policy, HSTS over TLS, `no-store`
   for `/api/`).
2. `http.ServeMux` dispatches on method and path (`"GET /api/lists/{id}"`).
   Anything that is not under `/api/` is served from the embedded client.
3. The route wrapper (`App.handle`) applies, in order: the per-address API
   rate limit; authentication (session cookie + CSRF header, or bearer
   token); the *pending step* gate (an account that must change its password
   or enrol MFA can only reach the account endpoints); the route's
   permission, if any.
4. The handler validates input (JSON body ≤ 1 MiB, unknown fields rejected),
   checks the caller's level on the resource, runs SQL (in a transaction when
   several statements belong together), writes an activity entry and
   publishes a change event.
5. Errors are returned as `{"error": "<code>"}` with an HTTP status. Internal
   errors are logged with a reference and never shown to the client.

## Data model

All identifiers are 128-bit hex strings generated by the application: 48
bits of creation time in milliseconds followed by 80 random bits (the UUIDv7
idea). They are unguessable, and sorting by id gives creation order, which
is used for stable ordering and paging. Anonymous ballots are the exception:
their ids are fully random so nothing about the voting time can be derived.
Timestamps are unix seconds (UTC). Booleans are 0/1 integers.

| Area | Tables |
|------|--------|
| Accounts | `users` (PII columns encrypted), `sessions` (token hashes), `roles`, `role_perms`, `user_roles` |
| Groups | `groups` (scope `global` or `local`), `group_members` |
| Sharing | `acl` (resource type + id → subject → level) |
| Files | `files` (metadata; content lives in the blob store) |
| Chat | `channels` (kind `channel` or `dm`), `messages`, `message_files`, `channel_reads` |
| Documents | `documents`, `doc_versions` |
| Lists | `lists`, `list_items` |
| Polls | `polls`, `poll_options`, `ballots`, `ballot_choices`, `poll_voters` |
| Calendar | `events` |
| Meetings | `meetings`, `agenda_items` |
| Decisions | `decisions`, `decision_revisions` |
| Boards | `boards`, `board_columns`, `cards` |
| History | `activity` (personal history; rows with `audit=1` form the audit log) |
| Other | `settings` (reserved), `schema_migrations` |

Migrations are an ordered list in `internal/db/schema.go`; they are applied
automatically at start-up and recorded in `schema_migrations`.

## Access model

Two layers decide what a user may do.

**Permissions** come from roles and gate organisation-wide capabilities:
`users.manage`, `roles.manage`, `logs.view`, `backup.manage`,
`channels.create`, `content.moderate`, `decisions.create`,
`meetings.create`. Built-in roles: *admin* (all), *leader* (the last four),
*member* (none). Administrators can define more roles.

**Sharing** decides who can see and change each resource. Eight resource
types share one mechanism: channel, document, list, poll, event, meeting,
decision, board. Every resource has an owner and zero or more shares in the
`acl` table:

```
(res_type, res_id) → subject (all | group | role | user) → level (1 read, 2 write)
```

* No shares = private to the owner.
* The owner has level 3 (manage): edit, share, delete.
* `content.moderate` gives level 3 on resources that are *already shared* —
  never on private resources or direct messages.
* Administrators have **no implicit access** to other people's content.
* Read access that is missing is reported as *not found*, so the existence of
  a resource is not revealed.

List endpoints use one SQL condition (`visible()` in `acl.go`) and single
resources use `level()`; search reuses the same condition, so the three can
not drift apart. What "write" means per type: post in a channel, add
versions to a document, edit items of a list, edit cards on a board, edit an
event or a meeting's agenda and protocol. Anyone with read access to a poll
may vote.

Direct messages are channels of kind `dm` without owner, where each
participant has a write share; their sharing cannot be changed.

A meeting owns a calendar event. The event's shares are copied from the
meeting (read only) whenever the meeting's sharing changes.

## Live updates

`GET /api/events` is a Server-Sent Events stream. When something changes the
server publishes `{type, id}` — no content. Before an event is written to a
client's stream, the server checks that this user can read the resource. The
client reacts by re-fetching what it currently shows. Slow clients simply
miss events and catch up on the next one.

## Storage abstraction

**Database.** `internal/db` runs the same SQL on SQLite (pure Go driver
`modernc.org/sqlite`, WAL mode, foreign keys, `secure_delete`) and PostgreSQL
(`pgx`). Portability rules: `?` placeholders (rebound to `$n`), only
`TEXT`/`INTEGER`/`BIGINT` columns, application generated ids, unix
timestamps, `ON CONFLICT` upserts, no vendor specific functions.

**Files.** `blob.Backend` (`Put`, `Get`, `Delete`, `List`) has two
implementations: a directory tree under `<data_dir>/blobs` and any S3
compatible store. `blob.Store` wraps the back-end and encrypts every object
with AES-256-GCM before it is written, so the back-end only ever sees
ciphertext. Files are immutable; messages and document versions reference
them, and unreferenced files are garbage collected.

**Backups** are database independent (rows as JSON), so a backup from SQLite
restores into PostgreSQL and the other way round.

## Web client

* **Preact + htm**, loaded as native ES modules. No build step, no npm at
  build time: the one dependency is vendored in
  `web/static/vendor/htm-preact-standalone.js`.
* Works under a strict Content-Security-Policy (`script-src 'self'`, no
  inline script, no `eval`).
* Hash based routing (`#/chat`, `#/documents`, …), so the server only serves
  static files and the API.
* Translations are plain modules (`web/static/js/i18n/en.js`, `sv.js`); the
  language is switched at runtime and stored in the user's profile.
* Themes (light, dark, spring, autumn, sand, contrast), text size and
  accessibility options are CSS custom properties toggled on the root
  element and stored in the profile.
* A web app manifest and a minimal service worker make the client
  installable. The service worker deliberately caches nothing: all data is
  access controlled and always fetched from the server.

## Mobile strategy

The browser client is responsive and installable as a PWA today. Native
iOS/Android apps can use the same REST API with bearer tokens
(`POST /api/auth/login` with `"token": true`), either as a thin wrapper
around the web client or as fully native clients. See [mobile.md](mobile.md).

## Scaling notes

The design targets clubs and associations: tens to a few thousand members on
one small server. One process holds the SSE hub and the rate limiters in
memory, so it is a single-instance design. Search scans rows instead of
using an index. Both are deliberate MVP choices, see
[design-decisions.md](design-decisions.md).
